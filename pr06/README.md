# ПР-6. Синхронизация потоков

## Цель

Показать race condition и исправить его; реализовать bounded buffer двумя способами, reusable barrier и lost wakeup.

## Запуск

```bash
python3 race.py
python3 fixed.py
python3 sync.py semaphore
python3 sync.py condition
python3 sync.py barrier
python3 sync.py lost-wakeup
```

Буфер имеет ёмкость 5. Запускаются 3 производителя и 2 потребителя, всего обрабатывается 1000 элементов. Sentinel сообщает потребителям о завершении; `assert` проверяет количество и уникальность данных.

## Контрольный результат

```text
race:    Результат: 400000; ожидалось: 400000; время: 0.020 с
fixed:   Результат: 400000; ожидалось: 400000; время: 0.190 с
semaphore: OK; элементов=1000; переполнений=0; повторов=0
condition: OK; элементов=1000; переполнений=0; повторов=0
barrier: OK; 4 потока прошли 3 синхронизированные фазы
if: consumed=True, ready=False — ложное потребление
while повторно проверил бы ready и не позволил бы продолжить
```

В этом запуске планировщик случайно не проявил потерю обновлений в `race.py`, поэтому результат совпал с ожидаемым; при другом чередовании потоков он может стать меньше 400000. В `fixed.py` весь инкремент защищён одним `Lock`.

## Вывод

Операция `counter += 1` не атомарна: потоки могут прочитать одно старое значение и потерять часть обновлений. Мьютекс делает критическую секцию взаимоисключающей. Семафоры `empty/full` ограничивают число свободных и занятых мест; condition связывает ожидание с проверкой предиката под мьютексом. Барьер можно переиспользовать благодаря счётчику поколений.

**Почему condition требует цикл `while`?** После пробуждения условие могло снова стать ложным из-за другого потока или ложного пробуждения.

**Что такое lost wakeup?** Уведомление отправлено до начала ожидания и не сохранено; следующий `wait()` может ждать бесконечно, поэтому состояние проверяется в цикле.
